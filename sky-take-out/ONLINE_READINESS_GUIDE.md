# 上线与并发准备指南

> 适用项目：当前手机商城改造版项目
> 目标场景：阿里云 `2C4G` 服务器，稳定支撑 `100+` 在线并发请求
> 更新时间：2026-03-09

---

## 1. 目标说明

这里的“100+ 并发”建议按下面的目标理解：

- 日常浏览、搜索、购物车、订单查询可以稳定响应
- 高峰期同时有 100 人以上访问时，系统不出现大面积超时
- 核心链路包括：
  - 商品列表
  - 商品搜索
  - 加入购物车
  - 购物车查看
  - 提交订单
  - 后台订单管理

对于 `2C4G` 机器，这个目标是可以争取的，但前提是先完成基础优化，而不是直接上线硬扛。

---

## 2. 上线前必须完成

### 2.1 配置与安全

- 将数据库、Redis、OSS、微信等敏感配置改为环境变量或服务器私有配置
- 区分 `dev / test / prod` 配置，避免生产环境继续使用本地开发配置
- 更换开发阶段使用过的密钥、Token 密钥、云服务 AccessKey
- 关闭不必要的调试配置，例如过度详细的 SQL 日志、调试接口、测试账号
- 确认 `Swagger / Knife4j` 在生产环境默认关闭，或仅内网可访问

### 2.2 Nginx 反向代理

- 使用 Nginx 作为统一入口
- 管理端前端静态资源交给 Nginx 托管
- Spring Boot 仅暴露内部端口，例如 `8080`
- 配置基础 gzip、静态缓存、反向代理超时
- 增加简单限流，优先保护搜索、登录、下单接口

推荐结构：

- `Nginx`
- `Spring Boot`
- `MySQL`
- `Redis`
- `OSS`

### 2.3 数据库索引

以下字段建议重点检查并补索引：

- `product(category_id, status)`
- `product(phone_model_id)`
- `product(name)`
- `orders(user_id, status, order_time)`
- `orders(number)`
- `order_detail(order_id)`
- `shopping_cart(user_id)`
- `stock(product_id)`

说明：

- 搜索接口如果继续用模糊查询，`name / brand / model` 的检索效率要重点观察
- 如果后面搜索量明显增加，建议单独做搜索优化，不要长期只靠 `%keyword%`

### 2.4 Redis 缓存

至少缓存这几类读多写少的数据：

- 商品分类列表
- 商品列表
- 热门商品或推荐商品
- 店铺营业状态
- 热门搜索词

同时要补好缓存失效策略：

- 商品新增、修改、上下架后主动删除相关缓存
- 分类变更后删除分类和商品列表缓存
- 门店状态变更后立即删除状态缓存

### 2.5 日志与异常处理

- 统一接口异常返回格式
- 生产环境避免打印敏感信息
- SQL 日志不要全量输出
- 为登录、下单、库存、订单状态流转记录关键日志
- 保留错误日志文件滚动策略，避免磁盘被打满

### 2.6 服务器基础环境

- 使用 Linux 服务器部署，不建议生产继续跑在开发机环境
- 统一 JDK、MySQL、Redis、Nginx 版本
- 设置服务器时区、字符集、文件句柄数
- 开启基本防火墙，仅放行必要端口
- 为 MySQL、Redis 设置开机自启

## 3. 为了 100+ 并发必须做的性能优化

### 3.1 商品列表接口优化

这是最容易成为热点的接口之一。

必须做到：

- 只查展示所需字段，不要一次返回过多冗余信息
- 分页返回
- 分类切换时避免重复查相同数据
- 优先走 Redis 缓存
- 图片走 OSS，不走本机文件系统

### 3.2 搜索接口优化

搜索最容易拖慢数据库。

建议第一阶段先这样做：

- 限制每次返回条数，例如 `10` 或 `20`
- 空关键字不查询
- 增加 300ms 防抖，前端已具备基础条件
- 热门词结果可做短时缓存
- 对高频搜索词做日志统计

如果后面搜索量继续上涨，再考虑：

- 前缀匹配优先
- 搜索专用表
- Elasticsearch 或其他搜索方案

### 3.3 购物车与订单链路优化

核心目标是缩短写请求耗时。

建议：

- 购物车列表只按当前用户查询
- 下单时减少重复查库
- 订单详情、订单明细查询避免 N+1
- 非核心动作异步化，例如消息通知、统计刷新
- 库存扣减逻辑要简单直接，避免复杂事务链过长

### 3.4 后台管理接口优化

管理端虽然并发通常不如用户端高，但容易出现重查询。

重点关注：

- 订单列表分页查询
- 订单详情查询
- 统计页接口
- 图表时间区间查询

建议：

- 统计类接口做缓存
- 大时间范围查询限制范围
- 首页统计数据合并查询，避免多个接口重复扫表

## 4. JVM 与服务参数建议

`2C4G` 不适合把堆开太大，要给系统、MySQL、Redis、Nginx 留空间。

建议起步参数：

```bash
JAVA_OPTS="-Xms512m -Xmx1024m \
-XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=256m \
-XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
-XX:+HeapDumpOnOutOfMemoryError \
-Dfile.encoding=UTF-8"
```

建议原则：

- JVM 堆先控制在 `512MB ~ 1GB`
- 不要一开始就把内存全给 Java
- Tomcat 线程数不要盲目开大
- 连接池大小按实际压测结果调，不要超过数据库承载

可以先参考：

```yaml
server:
  tomcat:
    threads:
      max: 80
      min-spare: 10
    accept-count: 100

spring:
  datasource:
    hikari:
      maximum-pool-size: 15
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

注意：

- 这些不是最终值，必须结合压测调整

## 5. MySQL 建议

### 5.1 必做项

- 使用 InnoDB
- 所有表字符集统一 `utf8mb4`
- 打开慢查询日志
- 检查所有高频 SQL 的执行计划
- 避免全表扫描

### 5.2 小机器建议

对 `2C4G`，MySQL 不建议配置过猛，可先从保守值开始：

```ini
[mysqld]
max_connections = 100
innodb_buffer_pool_size = 512M
innodb_log_file_size = 128M
innodb_flush_log_at_trx_commit = 2
thread_cache_size = 16
tmp_table_size = 32M
max_heap_table_size = 32M
slow_query_log = 1
long_query_time = 1
```

说明：

- 真正瓶颈通常不是 `max_connections` 不够，而是慢 SQL 太多

## 6. Redis 建议

Redis 在这个项目里主要承担“减数据库压力”。

建议：

- 独立密码
- 合理设置 `maxmemory`
- 使用 `allkeys-lru` 或按场景设置淘汰策略
- 热点数据设置过期时间
- 避免把大对象、无边界列表长期塞进 Redis

适合放 Redis 的内容：

- 商品列表缓存
- 分类缓存
- 店铺状态
- 热门搜索
- 登录限流计数
- 验证码或短期 Token 辅助信息

---

## 7. 对象存储与图片

图片资源不要走本机磁盘直连下载。

建议：

- 商品图片全部走 OSS
- 前端直接访问 OSS 或 CDN 地址
- 缩略图和原图分离
- 后台上传时限制格式和大小
- 清理无效图片链接，避免频繁 404

---

## 8. 监控与告警

没有监控，就很难知道 100 并发时到底卡在哪。

上线前至少准备：

- CPU、内存、磁盘、带宽监控
- JVM 堆内存与 Full GC 次数
- MySQL 慢查询日志
- Redis 内存占用
- Nginx 访问日志与 5xx 统计
- 核心接口响应时间

建议优先关注的接口：

- `/user/product/list`
- `/user/product/search`
- `/user/shoppingCart/list`
- `/user/order/submit`
- `/admin/order/conditionSearch`

## 9. 压测方案

### 9.1 压测前提

- 使用接近生产环境的数据量
- 至少准备真实商品、订单、购物车数据
- Redis 与 MySQL 都使用部署环境实例
- 不要只测首页，重点测热点接口

### 9.2 建议压测顺序

第一阶段：

- 30 并发
- 50 并发
- 80 并发

第二阶段：

- 100 并发
- 120 并发
- 150 并发

### 9.3 建议重点压测接口

- 商品列表
- 商品搜索
- 加入购物车
- 购物车列表
- 提交订单
- 后台订单分页

### 9.4 压测结果重点看什么

- 平均响应时间
- P95 / P99 响应时间
- 错误率
- CPU 占用
- MySQL 慢查询
- Redis 命中率

目标建议：

- 普通查询接口 `P95 < 500ms`
- 搜索接口 `P95 < 800ms`
- 下单接口 `P95 < 1000ms`
- 错误率尽量控制在 `1%` 以下

## 10. 建议的上线步骤

### 第一阶段：上线前整理

- 完成配置脱敏
- 关闭生产环境调试项
- 补索引
- 接入 Redis 缓存
- 补全 Nginx 配置
- 做第一次压测

### 第二阶段：试运行

- 先用测试域名部署
- 做功能回归
- 做 50~100 并发压测
- 观察 CPU、内存、慢 SQL
- 修复最慢的 3~5 条接口

### 第三阶段：正式上线

- 低峰时段发布
- 保留回滚包
- 重点盯登录、搜索、商品列表、下单、后台订单接口
- 首日持续观察日志和数据库负载

## 11. 当前项目最值得优先补的点

结合当前项目状态，建议你优先做下面这些：

### 必须先做

- 配置脱敏与生产配置拆分
- 商品、订单、购物车、库存相关索引检查
- 商品列表与分类缓存
- 搜索接口限流与缓存
- Nginx 反向代理
- 慢查询日志

### 很建议做

- 后台统计接口缓存
- 下单链路日志梳理
- OSS 图片统一检查
- 登录失败限制与风控
- 生产环境监控面板

### 后续再做

- 搜索专项优化
- 订单消息异步化
- CDN
- 读写分离或应用拆分
- 多实例部署

---

## 12. 最终建议

如果你的目标是“先稳定上线，再逐步放量”，最合理的路线是：

1. 先把单机 `2C4G` 做到稳定支撑 `50~100` 并发
2. 再通过缓存、索引、慢 SQL 优化把峰值推到 `100+`
3. 如果后面业务继续增长，再考虑：
   - 应用多实例
   - Nginx 负载均衡
   - 独立数据库与 Redis
   - 搜索服务拆分

对于你现在这个项目，真正决定能不能扛住并发的，不是页面数量，而是：

- 商品列表查得够不够轻
- 搜索有没有拖库
- 下单事务是不是过长
- Redis 有没有真正用起来
- 慢 SQL 有没有提前解决

只要把这几项做好，`2C4G` 跑一个 100+ 并发的中小型商城首版，是有机会稳住的。
